# 抽取后校验规则（业务确认稿）

给周一业务会用。本文件只定「抽完一张报关单之后查什么、查不过怎么办」。

还不接引擎。确认后的位数 / 正则 / 容差再写进 `fields.yaml`（或独立规则 YAML），由 [#20](https://github.com/Baldwinzc/docparse/issues/20) 执行。加一条规则不应改 Python。

本地对眼（确认后才有）：`python -m docparse.cli declare file.xlsx` 的 `_meta.review_reasons`。

## 原则（已定，会上不必再议）

| 原则 | 含义 |
|---|---|
| 不编造 | 查不过标 `needs_review`，**不改写成「看起来合法」的值** |
| 空不当错 | 本期不区分必填 / 选填。没抽到 = 空，不因「没填」判失败 |
| 有值才查 | 字段有字才跑格式 / 码表 / 交叉。空字段跳过该条 |
| 失败带证据 | 规则名 + 原文；不静默丢掉 |
| 码表查不到不改 | 已转成 code 的必须能反查；查不到复核，值留着 |
| 规则在数据文件 | 精确位数 / 正则 / 容差不写死在 Python |

组装层已经会打复核、本层不要重复发明的：

- 无草单时监管方式 / 征免 / 口岸 / 包装种类空着（`customs_empty`）
- 名称转不出 code（`unknown_code` / `code_table_pending`）
- 草单和箱单件毛净对不上（`head_mismatch`）
- 只有净重、没有毛重（`net_is_not_gross`）
- 申报要素原文不编 `0\|0\|...`

本层是**再加一道闸**：位数不对、毛 < 净、单价 × 数量对不上、假 code。

## 建议默认（请打勾）

下面每条都是「建议默认」。对就留；不对改右边「业务口径」。没拍板的不进引擎。

### B. 码表

| # | 规则 | 建议默认 | 业务口径 | 确认 |
|---|---|---|---|---|
| B1 | 已转成 code 的字段 | 必须能在对应表 `reverse(表, code)` 查到名称 | | ☐ |
| B2 | 查不到 | `needs_review` + `code_not_in_table`，**不改值** | | ☐ |
| B3 | pending 表（币制 / 报关单类型 / 入境离境口岸） | 本轮**不查枚举**（表还没有）。只查 A 里的位数（若已确认） | | ☐ |

### C. 交叉（两边都有值才比）

| # | 规则 | 建议默认 | 业务口径 | 确认 |
|---|---|---|---|---|
| C1 | 表头毛净 | `grossWt ≥ netWt`。缺一边（含只有净重）不比 | | ☐ |
| C2 | 货行毛净 | 同行 `customGrossWet ≥ customNetWt`。缺一边不比 | | ☐ |
| C3 | 件数 | `packNo > 0` | | ☐ |
| C4 | 单价 × 数量 ≈ 总价 | 同行 `declPrice × gqty` 与 `declTotal` 相对误差 ≤ **0.5%**，且绝对误差 ≤ **0.05**（兼顾两位小数和四舍五入）。三值缺一不比 | | ☐ |
| C5 | 表头净重 vs 货行合计 | 两边都有则 `|netWt − Σ customNetWt|` 相对 ≤ **1%** 或绝对 ≤ **0.05 kg** | | ☐ |
| C6 | 表头毛重 vs 货行合计 | 同 C5，对 `grossWt` / `Σ customGrossWet` | | ☐ |
| C7 | 表头件数 vs 货行 | **本轮不做**。货行没有箱数槽，件数在表头 | | ☐ |
| C8 | 表头金额 vs 货行总价合计 | **本轮不做**。表头没有总价槽 | | ☐ |

重量比较用去逗号后的数字，单位当千克，不换算。

### D. 失败怎么出门

| # | 规则 | 建议默认 | 业务口径 | 确认 |
|---|---|---|---|---|
| D1 | 单字段格式 / 码表失败 | 该字段 `needs_review`（或 `invalid`），值保留原文 | | ☐ |
| D2 | 交叉失败 | 相关字段都标复核，理由挂在整单 `review_reasons` | | ☐ |
| D3 | 整单状态 | 有任一条失败 → 整单 `needs_review`，JSON 仍输出，不丢单 | | ☐ |
| D4 | 已有组装复核 | 保留，本层只追加，不覆盖 | | ☐ |

## 会上请拍板的 6 个关键点

1. **海关编号 / 预录入编号是不是 18 位数字？** 空是否一律放行？
2. **HS 锁 10 位，还是 8–10 都算合法？**
3. **海关 10 位代码允许字母吗？**（恒信样本 `441394164D`）
4. **信用代码要不要校验第 18 位校验位？** 建议本期只查长度。
5. **单价 × 数量的容差**用 0.5% / 0.05，还是更严（差 1 分钱就拦）？
6. **表头重量和货行合计**要比吗？容差 1% / 0.05 kg 是否够？

## 本轮明确不做

| 项 | 为什么 |
|---|---|
| 必填 / 选填 | #12 已定本期不区分 |
| 改值「修」成合法 | #20 范围写死了 |
| 运费 / 航次 / 唛码拆开再验 | #34–#36 |
| 发票号进表头再验 | #37 |
| 币制 / 报关单类型 / CIQ 口岸枚举 | 码表还没有 |
| 申报要素 `0\|0\|...` | #18 已留原文 |
| 按公司写规则 | 和整条链路一致 |
| 客户原件入库 | Epic 边界 |

## 以后新规则改哪（确认后、#20 落地时）

| 你看到的现象 | 改哪里 | 动 Python？ |
|---|---|---|
| 某个字段位数 / 正则不对 | `fields.yaml` 该字段的 `pattern` / `value_type` | 否 |
| 新交叉（例如件数 vs 箱数） | 规则 YAML 加一条，点两个字段名 | 否（引擎按目录跑） |
| 容差要改 | 规则 YAML 的 `tolerance` | 否 |
| 新码表要反查 | 字段已有 `code_table`；表补行 | 否 |
| 新字段要不要查 | 字段目录先收，再挂 pattern | 否 |
| 一种全新比较（校验位、日期先后） | 新 rule type + 一个函数 | 是，通用规则，不按公司 |

不要 `if company == "恒信"`。不要在引擎里写死 `18`、`10`、`0.005`。

## 夹具（确认后 #20 实现时）

| 夹具 | 期望 |
|---|---|
| 合法恒信形状 | 格式 / 码表 / 毛≥净通过（组装复核可仍在） |
| 海关编号位数不对 | 不能当成功值出门 |
| 毛重 < 净重 | 拦住 |
| 假 code（4 位关区写 `99`） | 拦住 |
| 单价 × 数量差出容差 | 拦住 |
| 只有净重、没有毛重 | **不**误报 C1（缺一边不比） |
