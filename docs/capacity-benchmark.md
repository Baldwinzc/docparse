# 容量与规格实测：并发 / 显存 / 时延（#98，父 #94）

本文是 #98 的**结论部分**：回答「**买什么机器**」。上游是 [#97 / #110](local-ocr-benchmark.md)（那个答「用哪个引擎」）——两者口径不同，别混读：

| | #110（local-ocr-benchmark.md） | 本文（#98） |
|---|---|---|
| 问的是 | 哪个引擎 / 哪个档位 **准** | 一张卡能扛多少 **量** |
| 引擎 | 8 个本地档位横比 | **只用第一期选型** `PP-OCRv6 small` + `doc-ori` |
| 并发 | 单进程串行 | **1 / 2 / 4 / 8 个进程**（按票分片） |
| 产出 | CER / 字段命中 / 显存 | **页/秒、票/秒、显存水位、P50/P95、采购换算** |

> **本文数据的定位：单机、单卡、单批样本的实测，不是生产 SLA。** 局限逐条写在 [§7](#7-局限这份数据不能当什么用)。

装置怎么用见 [benchmarks/ocr/README.md](../benchmarks/ocr/README.md)「容量与规格实测（#98）」一节；本文只讲结论与算账。

## 1. 结论（先看这个）

| 问题 | 结论 |
|---|---|
| **一张 4090 能扛多少** | 并发 1 时 **1.52 页/秒**；并发 8 时 **6.60 页/秒**（相对并发 1 是 **4.35×**，不是 8×）。 |
| **并发开到几** | **吞吐拐点在并发 2–4**：并发 2 有 88% 线性效率，并发 4 有 74%，并发 8 只剩 54%——加进程还在涨量，但每加一个换来的边际产出掉了一半，且单页时延从 455 ms 涨到 694 ms。 |
| **24 GB 够不够** | **远远够**。并发 8 时整卡峰值 **10.8 GB**（含基线 ~3.2 GB），**余量约 13.4 GB**；每 worker 增量约 **950 MB**。瓶颈不在显存。 |
| **无卡可用怎么办** | **CPU 上别用 Paddle，用 RapidOCR**：同机同档，RapidOCR CPU **1.63 s/页**，Paddle CPU **15.4 s/页**（**差 ~9×**）。且两者最优并发不同（见 §5）。 |
| **采购换算** | 见 §6。**日 1000 票（每票 4 页）用一张 4090、并发 1 就够，还有约 11× 余量**——本场景的瓶颈不在算力。 |
| **与云比回本** | 见 §6.3。回本天数 = 硬件价 ÷（日页数 × 云单价）。日 100 票这一档自建大概率回不了本；**但这套东西的第一性理由是数据不出网（#94），不是省钱**。 |

## 2. 跑数环境与口径

**机器**（与 #110 同一台自有远程机，非生产机）：

| 项 | 值 |
|---|---|
| 卡 | NVIDIA GeForce RTX 4090 24 GB（**固定 2 号卡**，`CUDA_VISIBLE_DEVICES=2`） |
| CPU | 48 核（`nproc=48`） |
| Python | 3.11.16 |
| paddlepaddle-gpu | 3.3.1（cu126 源） |
| paddleocr / paddlex | 3.7.0 / 3.7.2 |
| rapidocr / onnxruntime | 3.9.2 / 1.30.0（**CPU 版**） |
| 引擎 | `local:paddle-v6-small`（PP-OCRv6 small）+ `local:doc-ori` 方向分类，`--rotate-mode auto` |
| 样本 | **真机 8 页**（半岛 2 + 镇发 6），**2 票**，`--repeat 4` → **8 票 / 32 页**（#97 同批，原件不入库，路径走 `DOCPARSE_OCR_DEMO_DIR`） |
| 预热 | 每 worker `--warmup 2` 页，**不计入**吞吐与时延 |

**「一票」怎么算**：一票 = 一份原件 PDF（半岛 2 页、镇发 6 页，本批均值 **4 页/票**）。采购买卡时按**你自己的一票几页**折算。

**并发怎么建模**（读数字前必须知道，细节见 README）：

- **一个并发档 = N 个进程**，每进程一个引擎实例、**整票**处理自己分到的那几票（票不拆页，票级时延才有定义）。
- 票按**页数贪心配平**（LPT）分给 worker，避免短票/长票在轮转下把 makespan 拉偏。
- **父进程不加载模型**，只备图 / 起进程 / 采样；worker 建好引擎、预热完，父进程等齐所有 `ready` 再落 `go`——**模型加载与预热都在计时之外**。
- 吞吐 = 总页数 ÷ makespan（`max(worker 结束) − go`），所以是**稳态吞吐**，不是含启动的端到端。

**显存两个口径**（不是一回事，报告里都留）：

| 口径 | 怎么读 | 表示什么 |
|---|---|---|
| **整卡** | 父进程 `nvidia-smi -i 2` 轮询 0.2 s | 这张卡**总共**占了多少——含同卡其它进程。**24 GB 的水位看这个。** |
| **进程** | 每 worker `paddle.device.cuda.max_memory_allocated()` | 该进程模型本体的净占用（不含 CUDA context 与碎片）。N 个相加 = 模型侧下限。 |

> 跑数期间 2 号卡无其它进程（基线约 **3.2 GB** 是卡本身的固定占用，整卡合计 24.5 GB 里剩的就是可用水位）；`--device cpu` 档**不读显存**（无关，且会读到同一台机上被别人占的卡）。

## 3. GPU 曲线（4090 24 GB）

| 并发 | 页/秒 | 票/秒 | 单页 P50/P95 (ms) | 单票 P50/P95 (ms) | 整卡峰值 (MB) | 进程峰值/合计 (MB) | 相对并发 1 | 失败 |
|---|---|---|---|---|---|---|---|---|
| 1 | 1.5172 | 0.3793 | 455 / 1236 | 2580 / 2980 | 4157 | 329 / 329 | 1.00× | 0 |
| 2 | 2.6899 | 0.6725 | 492 / 1311 | 2789 / 3247 | 5114 | 329 / 657 | 1.77× | 0 |
| 4 | 4.4810 | 1.1202 | 530 / 1551 | 3175 / 3618 | 7023 | 329 / 1315 | 2.95× | 0 |
| 8 | 6.6026 | 1.6507 | 694 / 1865 | 3925 / 4567 | 10838 | 329 / 2630 | 4.35× | 0 |

**怎么读这三件事**：

1. **吞吐是次线性的**（并发 2/4/8 分别是 1.77× / 2.95× / 4.35×）。单纯堆进程换不来线性扩容——单卡上多个 worker 争同一份算力与显存带宽。
2. **多进程是拿时延换吞吐**：并发 8 时单页 P50 是并发 1 的 **1.5×**（455 → 694 ms），单票 P50 也是 **1.5×**（2.58 → 3.93 s）。**下游（#99 接进来之后）若对单票时延敏感，并发别开满。**
3. **显存不是瓶颈**：整卡峰值 10.8 GB，**余量约 13.4 GB**。按每 worker ~950 MB 增量线性外推，24 GB 理论可塞 ~20 个 worker——**但吞吐拐点早在并发 2–4**，所以「卡能塞几个」不是该问的问题，「并发开到几边际产出最高」才是。

**边际产出**（每多一个 worker 多出来的页/秒）：

| 扩容 | 新增页/秒 | 每 worker 增量 |
|---|---|---|
| 1 → 2 | +1.17 | 1.17 |
| 2 → 4 | +1.79 | 0.90 |
| 4 → 8 | +2.12 | 0.53 |

## 4. 时延分位为什么单列

报 P50/P95 而不是均值，是因为**均值会被长尾掩盖**。本批真机页里，镇发那几页是大幅面扫描件（含两页内容旋转 90°、要走方向分类 + 旋转），单页耗时明显高于半岛——只看均值会把这条尾巴抹掉。上表里 P95 普遍是 P50 的 **2.4–2.7×**，就是这条尾巴。

> 口径提醒：这里的单页时延**含方向分类**（`--rotate-mode auto` 是生产配置）。要做 A/B（不判方向）对照，用 #110 的装置，不在本文。

## 5. CPU 曲线（无卡可用场景）

**两条 CPU 路线都跑了——它们的结论方向不一样，只跑一条会得出错的并发建议。**

### 5.1 Paddle PP-OCRv6 small（与 GPU 同引擎）

| 并发 | 页/秒 | 票/秒 | 单页 P50/P95 (ms) | 单票 P50/P95 (ms) | 相对并发 1 |
|---|---|---|---|---|---|
| 1 | 0.0497 | 0.0124 | 15383 / 40146 | 80109 / 87555 | 1.00× |
| 2 | 0.0904 | 0.0226 | 16176 / 44538 | 87338 / 93993 | 1.82× |
| 4 | 0.1670 | 0.0417 | 18426 / 46790 | 94369 / 99977 | 3.36× |
| 8 | 0.2692 | 0.0673 | 20896 / 54863 | 110611 / 118622 | 5.42× |

> 每 worker 限 `cpu_threads=8`（`--cpu-threads 8`）。48 核机器上并发 6 之后开始超订，c8 是 64 线程跑 48 核——**已知超订，仍在涨**，说明这颗 CPU 到 c8 还没喂饱。

### 5.2 RapidOCR v6 small（ONNX Runtime CPU，等价退路）

| 并发 | 页/秒 | 票/秒 | 单页 P50/P95 (ms) | 单票 P50/P95 (ms) | 相对并发 1 |
|---|---|---|---|---|---|
| 1 | 0.5009 | 0.1252 | 1630 / 3258 | 7965 / 9583 | 1.00× |
| 2 | **0.6515** | 0.1629 | 2386 / 5422 | 11938 / 14931 | **1.30×** |
| 4 | 0.4993 | 0.1248 | 5579 / 15053 | 30886 / 33019 | 1.00× |
| 8 | 0.4044 | 0.1011 | 14719 / 37204 | 75300 / 79063 | **0.81×** |

### 5.3 三条本地路线的量级

| 路线 | 最佳档 | 页/秒 | 单页 P50 |
|---|---|---|---|
| **4090 GPU** | 并发 8 | **6.60** | 694 ms |
| 4090 GPU | 并发 4 | 4.48 | 530 ms |
| **RapidOCR CPU** | 并发 2 | **0.65** | 2386 ms |
| Paddle CPU | 并发 8 | 0.27 | 20896 ms |

**三个结论**：

1. **GPU 比 CPU 快约 10×（对 RapidOCR）到 24×（对 Paddle CPU）。** 这个量级差是采购决策的主轴。
2. **CPU 上别用 Paddle，用 RapidOCR**：同机同档比，RapidOCR **1.63 s/页**、Paddle **15.4 s/页**，**差 ~9×**。原因是这台环境的 Paddle-CPU 被迫关掉了 MKL-DNN（Paddle 3.3.1 CPU + MKL-DNN + 新 IR 直接崩，见 §7.4），而 RapidOCR 走 onnxruntime CPU 的优化内核。**这条最反直觉，也最该记住。**
3. **两条 CPU 路线的最优并发相反**：RapidOCR 在**并发 2 见顶、c4 起掉头向下**（onnxruntime 每个进程自己就吃满多核，再起进程是互相抢核）；Paddle 我们每 worker 限了 8 线程，到 c8 仍在涨。**CPU 的最佳并发取决于引擎自己怎么用线程，不能照搬 GPU 的「越高越好」。**

## 6. 采购换算

### 6.1 单卡 / 单机日产能（8 小时窗口 = 28,800 s）

| 配置 | 页/秒 | 页/日（8h） | 票/日（4 页/票） |
|---|---|---|---|
| 4090 并发 1 | 1.52 | ~43,700 | ~10,900 |
| 4090 并发 4 | 4.48 | ~129,100 | ~32,300 |
| 4090 并发 8 | 6.60 | ~190,200 | ~47,500 |
| RapidOCR CPU 并发 2 | 0.65 | ~18,800 | ~4,700 |
| Paddle CPU 并发 8 | 0.27 | ~7,750 | ~1,900 |

### 6.2 需求档 → 需要什么

给定「日 N 票、每票 4 页」，算出需要的页/秒，再对到配置（余量 = 该配置吞吐 ÷ 需求）：

| 日票量（4 页/票） | 需要页/秒 | 4090 | RapidOCR CPU | Paddle CPU |
|---|---|---|---|---|
| **100** | 0.014 | 并发 1，余量 ~109× | 并发 1，余量 ~36× | 并发 1，余量 ~3.6× |
| **500** | 0.069 | 并发 1，余量 ~22× | 并发 1，余量 ~7.2× | 并发 2，余量 ~1.3×（c1 不够） |
| **1000** | 0.139 | 并发 1，余量 ~11× | 并发 1，余量 ~3.6× | 并发 4，余量 ~1.2× |

**结论**：

- **本场景（扫描报关单，日 100–1000 票）用一张消费级卡就绰绰有余，余量在 10× 以上——瓶颈不在算力。** 真上线时该盯的是 PDF 渲染、版面重建（#62）、规则链这些 CPU/IO 环节，不是 OCR 推理。
- 若**坚持无卡**：**RapidOCR CPU 起 1–2 个进程**即可覆盖到 1000 票/日（余量 3.6×），单页时延 1.6 s。**别用 Paddle CPU**——要 4–8 个进程才够同一档，单页时延 15 s 以上。
- 换「每票页数」很简单：把上表的页/秒乘以 `(M/4)` 再比。票页越多，越该往 GPU 走。

### 6.3 与云单价的回本点

TextIn 通用 **0.04–0.058 元/页**（#60 已核对，见 [ocr-benchmark.md](ocr-benchmark.md) §5）。同口径折算（按 4 页/票）：

| 日票量 | 日页数 | 云成本/日 (0.04) | 云成本/日 (0.058) | 云成本/年（0.04 × 300 天） |
|---|---|---|---|---|
| 100 | 400 | 16 元 | 23.2 元 | 4,800 元 |
| 500 | 2,000 | 80 元 | 116 元 | 24,000 元 |
| 1000 | 4,000 | 160 元 | 232 元 | 48,000 元 |

**回本天数 = 硬件总价 ÷ 日云成本**（按 0.04 元/页）：

| 日票量 | 硬件 2 万 | 硬件 5 万 | 硬件 10 万 |
|---|---|---|---|
| 100 | 1,250 天 | 3,125 天 | 6,250 天 |
| 500 | 250 天 | 625 天 | 1,250 天 |
| 1000 | 125 天 | 313 天 | 625 天 |

（单价取 0.058 时回本更快：日 1000 票、硬件 2 万 → **86 天**。）

> **硬件价我没写死**——4090 工作站、L4 / L20 服务器、二手机各是一档价，按你拿到的正式报价填这一列。上表只给公式，别把「2 万」当成结论。
>
> 另外：**4090 是消费卡，不适合 24×7 生产**（功耗、驱动、质保、无 ECC）。真上线按服务器卡（L4 / L20 / A10 一类）询价——它们的单卡吞吐会低于 4090，但**上面 §6.2 的 10× 余量足够吸收这个折扣**。

**这条要摆正**：#94 的第一性理由是**数据不出网**，不是省钱。日 100 票这一档，自建很可能**回不了本**（3 年往上）——但那不是否决它的理由，合规需求本身就值这个价。反过来，日 1000 票以上、且愿意上服务器卡，自建在 1–2 年内开始划算。

## 7. 局限（这份数据不能当什么用）

1. **单机、单卡、单批样本**：只有 **2 份原件 / 8 票 / 32 页**（真机，派生自 2 个 PDF）。这是「**能不能用**」的判据，**不是生产 SLA**，也不是「普遍可靠」的证明。
2. **机器是共享的**：跑数时整机 `load average ≈ 34`（48 核），上面有别人的任务在跑。**CPU 数字受邻居影响**，是这台机器当时的实测，不是干净基线；GPU 用 2 号卡，跑时该卡无其它进程（基线 ~3.2 GB 是卡本身占用），这一侧干净些。
3. **GPU 没测到饱和点**：并发 8 时吞吐仍在涨（4.35×），显存只用了 10.8 / 24.5 GB。所以 §3 的「拐点」是**按边际效率**说的，不是硬件上限；真要压满，得把并发推到 16+ 再测一轮。
4. **Paddle-CPU 数字是下界**：Paddle 3.3.1 上 CPU + MKL-DNN + 新 IR 会在 `predictor.run()` 抛 `ConvertPirAttribute2RuntimeAttribute`（`onednn_instruction.cc`），试过的 `FLAGS_*` 与 `engine_config` 都按不住，**只有 `enable_mkldnn=False` 能跑**（落在 `local_engines.paddle_cpu_kwargs`）。关掉 MKL-DNN 会慢一个量级——所以 §5.1 是**下限**，不是这台 CPU 的最优表现。CPU 上真正该看的是 §5.2 的 RapidOCR。
5. **时延含方向分类**（生产配置 `auto`）；装置里与云端对照用的 1.2 s 串行间隔**在本装置不适用**（容量装置不 sleep，否则吞吐被压塌）。
6. **端到端会更低**：这里只测 OCR 识别层。**伪格子（#62）/ 版面刀 / 表头与商品映射 / 组装 / 校验 / 最终报关单 JSON 的吞吐不在本文**——那是 #99 把引擎接进 `OcrClient` 之后才能测的。采购换算里的「票/秒」按纯 OCR 算，**上线后要按整条链路再打个折扣**。
7. **未覆盖类同 #110 §9**：不同来源的密集商品表、拍照件、更多横放件实例——这三类当前没有来源，本结论不外推到它们。

## 8. 复现

在跑数机器（已装 `.[local-ocr]`）的仓库根目录：

```bash
export DOCPARSE_OCR_DEMO_DIR=/path/to/既有真机样本目录
export HOME=/path/to/toolchain/home TMPDIR=/path/to/tmp   # 模型缓存与临时目录
PY=python   # 用跑数机器上装了 paddleocr / rapidocr 的那个解释器

# GPU 一条曲线（并发 1/2/4/8 一次跑完）
export CUDA_VISIBLE_DEVICES=2
$PY -m benchmarks.ocr.capacity run --device gpu \
    --engine local:paddle-v6-small --rotate-mode auto \
    --scope real --repeat 4 --warmup 2 --concurrency 1,2,4,8 \
    --run-dir out/capacity/gpu

# CPU 一条曲线：Paddle（与 GPU 同引擎，必须限线程 + 关 MKL-DNN，device=cpu 时自动）
$PY -m benchmarks.ocr.capacity run --device cpu \
    --engine local:paddle-v6-small --rotate-mode auto \
    --scope real --repeat 4 --warmup 2 --concurrency 1,2,4,8 --cpu-threads 8 \
    --run-dir out/capacity/cpu

# CPU 另一条：RapidOCR（ONNX Runtime CPU，CPU 上该用的那条）
$PY -m benchmarks.ocr.capacity run --device cpu \
    --engine local:rapidocr-v6-small --rotate-mode auto \
    --scope real --repeat 4 --warmup 2 --concurrency 1,2,4,8 \
    --run-dir out/capacity/cpu-rapid

$PY -m benchmarks.ocr.capacity report --run-dir out/capacity/gpu   # 汇表 → report.md
```

**口径**：`--repeat 4`（8 票 / 32 页）、`--warmup 2`（不计入）、吞吐按 makespan、时延按逐页 `elapsed_ms`。产物在 `benchmarks/ocr/out/capacity/`，**全部不入库**。

§2 的机器口径（48 核 / 4090 24 GB / paddle 3.3.1 / paddleocr 3.7.0 / rapidocr 3.9.2）与 §5.1、§5.2 的单页耗时一并登记在此，换机器重跑数字会变。
